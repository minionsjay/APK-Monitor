=== DEADBEEF+req_pq测试 ===

结果:
  DEADBEEF+msg_len+constructor+nonce(24B) → timeout(被接受!)
  DEADBEEF+auth_key_id(0)+msg_id+msg_len+constructor+nonce(40B) → EOF
  DEADBEEF空+req_pq → EOF

结论:
  握手消息格式: msg_len(4) + constructor(4) + data
  不需要auth_key_id和msg_id
  timeout说明服务端在等待更多数据
=== req_pq格式测试 ===

所有带msg_len的DEADBEEF+req_pq → timeout(被接受)
大payload(256B) → EOF
不带msg_len → timeout

可能服务端在等待完整的握手序列
需要发送多个DEADBEEF消息
=== req_pq最终测试 ===

所有格式的req_pq都返回timeout
服务端不响应任何格式的握手消息

测试的格式:
  1. DEADBEEF+msg_len+constructor+nonce → timeout
  2. 小端msg_len+小端constructor → timeout
  3. 分两次发送 → timeout
  4. 不同SNI → timeout
  5. 带padding → timeout
  6. 多消息 → timeout

结论:
  DH握手可能不走DEADBEEF通道
  或服务端需要特定认证才能响应
  auth_key来源仍然无法破解

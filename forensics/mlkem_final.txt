=== ML-KEM密钥交换确认 ===

证据:
1. GetKemKey, AddKemKeypair → KEM密钥管理
2. *mlkem.DecapsulationKey768 → ML-KEM-768
3. EncapsulatedKey, EncapsulationKey, Decapsulate → ML-KEM封装/解封装
4. Chrome115_PQ_PSK → PQ+PSK指纹
5. forwarderControlPSK → forwarder control的PSK
6. initPskExt → 初始化PSK TLS扩展
7. psk_dhe_ke → PSK+DHE密钥交换
8. base_nonce, kem_id → KEM参数

结论:
auth_key来自ML-KEM-768密钥交换
不是从TLS密钥(master_secret/preMasterSecret/EKM)派生
ML-KEM交换可能在DEADBEEF消息中或TLS自定义扩展中
自定义扩展0x3374/0x754f可能携带ML-KEM数据
但在截获的ClientHello中为空

ML-KEM-768:
- 公钥大小: 1184字节
- 密文大小: 1088字节
- 共享密钥: 32字节
- 这就是为什么auth_key_id是32字节的派生

完整加密流程:
1. TLS握手(标准TLS 1.2, cipher=0xc013)
2. ML-KEM交换(可能通过自定义扩展或DEADBEEF)
3. 获取32字节共享密钥
4. 共享密钥作为auth_key(补齐到256字节)
5. 用auth_key做MTProto加密
6. auth_key_id = 某种hash(auth_key)
=== auth_key = HKDF(ECDHE+ML-KEM) ===

关键发现:
  auth_key不是单独的preMasterSecret或ML-KEM
  auth_key = HKDF(ECDHE_shared + ML-KEM_shared)
  MlkemEcdhe = ML-KEM + ECDHE组合
  GetEcdheKey从ServerHello获取ECDHE
  GetKemKey获取ML-KEM
  这就是为什么preMasterSecret单独不匹配
=== SNI=sdk.01hd1.com测试 ===

SNI=sdk.01hd1.com → 仍返回302
服务端证书: CN=sdk.01hd1.com (Let's Encrypt)
SNI不是关键区别

最终结论:
  auth_key来自ML-KEM+ECDHE组合
  需要完全按照sendRequest的流程加密
  两次HMAC-SHA256 + 两次AES-256
=== 去掉ALPN测试 ===

去掉ALPN: cipher=0xc013 ALPN空
结果: 直接req_pq→302, DB+short→timeout, DB+req_pq→EOF
ALPN不是关键区别

=== 最终逆向总结 ===

auth_key来源: ML-KEM-768+ECDHE组合
加密流程: 2次HMAC-SHA256 + 2次AES-256-ECB
DEADBEEF格式: magic(4)+sublen(2)+payload_len(2)+pad_len(1)+padding+inner
inner格式: auth_key_id(8)+msg_key(16)+pad1(1)+enc_data(16k)
服务端证书: CN=sdk.01hd1.com (Let's Encrypt)
device_uuid: 94字符hex
constructor: req_pq=0x60469778

无法自行发送DH握手消息:
  1. auth_key_id=0 → EOF (服务端拒绝)
  2. auth_key_id=永久key → timeout (服务端不响应)
  3. 无auth_key_id → timeout (被接受但不响应)
  4. ML-KEM交换在TLS或DEADBEEF中(未确定)
=== Chrome115_PQ_PSK + OmitEmptyPsk ===

成功! cipher=0x1301 TLS1.3
KeyShareKeys: Ecdhe+Mlkem(set)+MlkemEcdhe
MasterSecret获取成功
DEADBEEF+req_pq → timeout(被接受)

需要限制TLS 1.2 + ML-KEM
=== X25519MLKEM768 + TLS 1.2 ===

cipher=0xc013 ver=0x0303 (TLS 1.2!) ✅
MasterSecret: 获取成功
DEADBEEF+req_pq → timeout(被接受)

关键: X25519MLKEM768在TLS 1.2中工作!
preMasterSecret可能包含ML-KEM+ECDHE组合

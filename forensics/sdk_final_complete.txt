完整节点获取流程：

阶段1: 获取控制面地址
  1. DNS TXT查询: _dns.{app_domain} → base64加密数据
  2. AES-CBC解密(key=AES_key, IV=key[:16]) → 控制面IP
     例: 43.248.2.74

阶段2: 获取代理节点
  方式A: .dat文件下载（主要方式）
    1. buildNodeDataURLs: 用域名+日期+shortMD5构建URL
    2. fetchByHeadThenGet: HTTP HEAD(检查ETag) → HTTP GET(下载)
    3. decryptNodeData: AES-CBC/GCM解密 → JSON{nodesA, nodesB}
  
  方式B: forwarder control（备选方式）
    1. collectBucketControlPlaneTargets: 随机选择控制面节点
    2. tryForwarderControlEndpoints: 尝试连接
    3. FetchForwarderFixedTuple: TLS+JSON+\n → 4B长度+JSON响应
    4. 需要配置forwarderControlPSK才能使用

阶段3: VPN代理转发
  1. APP用Android VPN API拦截所有流量
  2. 本地监听60139端口
  3. DEADBEEF封装: magic(4B)+sublen(2B)+payload_len(2B)+padding_len(1B)+padding+payload
  4. MTProto加密: auth_key_id(8B)+msg_key(16B)+encrypted_data (AES-IGE)
  5. TLS 1.2 (cipher=0xc013, SNI伪装)
  6. 连接到代理节点:30139

密钥体系：
  - AES-key: 32字节字符串 (如 htHtoU17cKxTjwVh1m2iyHfEI39RG1Cw)
  - RSA私钥: PEM格式, 编译时嵌入
  - device_uuid: hex(rand16B) + FormatInt(UnixNano, 36)
  - nonce: hex(rand16B) + FormatInt(UnixNano, 36)
  - label: hex(rand) + FormatInt(UnixNano, 10)
  - MAC: HMAC-SHA256(AES_key, strings.Join(8字段, 分隔符))

shortMD5算法:
  hex(md5(data))[:16] → 16字符hex

.dat URL构建:
  https://{shortMD5(domain+date)}.gz.bceos.com/{shortMD5(app_domain+AES_key)}.dat

DNS TXT解密:
  AES-CBC(key=AES_key, IV=key[:16]) → 明文IP地址

.dat文件解密:
  AES-CBC/GCM(key=AES_key) → JSON{nodesA, nodesB, nodesC, nodesD, nodesE}

TLS配置:
  - utls v1.8.2
  - HelloChrome_100 (可被自定义ClientHelloSpec替换)
  - TLSClientHelloMode: "hash" 或 "psk"
  - TLSHelloForDevice: "360Browser"
  - 自定义扩展: 0x3374 和 0x754f (空值)
  - ALPN: spdy/2, spdy/3, spdy/3.1, http/1.1
  - 压缩: DEFLATE(1) + NULL(0)
  - cipher列表: 0xc00a, 0xc014, 0xc013, 0x002f 等

forwarder control:
  - 发送: json.Marshal(fwdHelloRequest) + "\n"
  - 响应: 4字节大端长度 + JSON(fwdControlResponse)
  - MAC = HMAC-SHA256(AES_key, strings.Join(8字段, "."))
  - 字段: ["2", "hello", nonce, device_uuid, ts, ver_str, label, ""]
  - nonce = hex(rand16B) + FormatInt(UnixNano, 36)
  - label = hex(rand) + FormatInt(UnixNano, 10)
  - fwdHelloRequest字段: version, type, nonce, mac, device_uuid?, sdk_version?, timestamp_unix, A?, B?, C?, D?, E?
  - fwdControlResponse字段: version?, message?, nodesA, nodesB, nodesC, nodesD, nodesE, fixed, saved_at_unix
  - "not_modified"错误 → 使用缓存(304 Not Modified机制)

=== auth_key 突破分析 ===

关键发现：
1. auth_key_id = SHA1(master_secret)[:8]
   - 每次TLS连接master_secret不同 → auth_key_id不同
   - 这解释了为什么APP每次连接auth_key_id不同
   - MTProto标准: auth_key_id = lower64(SHA1(auth_key))

2. auth_key = TLS master_secret (48字节)
   - 从TLS握手的premaster_secret派生
   - 用KeyLogWriter可以获取
   - 格式: CLIENT_RANDOM <client_random> <master_secret>

3. SDK使用GODEBUG=tlsunsafeekm=1
   - 因为服务端不协商Extended Master Secret
   - 需要GODEBUG绕过EKM限制

4. SDK检查"reserved ExportKeyingMaterial label"
   - 某些EKM label被保留（不能使用）
   - 但auth_key可能直接用master_secret而不是EKM

5. MTProto加密流程：
   a. TLS握手 → 获取master_secret(48字节)
   b. auth_key = master_secret(或其变换)
   c. auth_key_id = SHA1(auth_key)[:8]
   d. AES-IGE加密: msg_key = SHA256(auth_key[0:32] + data)[0:16]
   e. encrypted = AES_IGE_Encrypt(auth_key, msg_key, data)

验证方法：
1. 在MITM代理中用KeyLogWriter获取APP的master_secret
2. 计算SHA1(master_secret)[:8]
3. 和APP的auth_key_id比较
4. 如果匹配 → auth_key = master_secret

=== auth_key 完整链路突破 ===

SDK密钥层级（从strings确认）：
1. TLS 1.3层:
   - tls13.EarlySecret
   - tls13.HandshakeSecret  
   - tls13.MasterSecret
   - tls13.ExporterMasterSecret
   - ExporterMasterSecret.Exporter()

2. TLS 1.2层:
   - masterSecret (48字节)
   - extMasterSecret (Extended Master Secret)
   - preMasterSecret (premaster secret)
   - SetMasterSecret (设置master_secret)
   - ExporterMasterSecret (导出master_secret)
   - ekmFromMasterSecret (从master_secret派生EKM)

3. SDK自定义层:
   - "crypto/tls: reserved ExportKeyingMaterial label" → 保留label检查
   - GODEBUG=tlsunsafeekm=1 → 绕过EKM限制
   - SDK修改了crypto/tls添加了直接访问master_secret的功能

4. tgnet.so层:
   - Connection::encryptKeyWithSecret(param)
     - param=0 → 不加密
     - param=2 → 用this+0x210(永久密钥=master_secret)
     - 其他 → 用this+0x58(临时密钥)
   - tgvoip_openssl_aes_ige_encrypt/decrypt
   - TL_bind_auth_key_inner → 绑定auth_key

5. auth_key_id计算:
   auth_key_id = SHA1(auth_key)[:8] (MTProto标准)
   auth_key = master_secret (48字节) 或其派生

6. 144字节hex参数:
   b3312fa7e23ee7e4988e056be3f82d19181d9c6efe8141120314088f5013875a...
   可能是某种固定参数或种子

验证方案:
1. 在MITM代理中用KeyLogWriter获取APP→代理的master_secret
2. auth_key_id_app = SHA1(master_secret)[:8]
3. 和MITM日志中的APP auth_key_id比较
4. 如果匹配 → auth_key = master_secret
5. 如果不匹配 → auth_key = EKM(some_label) 或其他派生

forwarder control EOF突破:
1. 可能APK未配置forwarderControlPSK
2. 可能需要用正确的控制面地址
3. 可能需要特定的TLS特征
4. 需要在MITM代理中截获APP的实际forwarder control流量
